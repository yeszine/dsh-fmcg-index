# PRD 撰写（prd-authoring）

把碎片化的产品输入，转化为产品、设计、研发三方无需猜测即可对齐的需求文档。

## 何时使用本技能

适用请求：

- 从零撰写 PRD，或对已有草稿做补全、重写、结构化；
- 把聊天记录、会议纪要、调研笔记、口头描述整理成正式需求；
- 为新产品、新模块或一次迭代定义功能范围与行为规则；
- 编写功能规格：用户流程、字段、状态、权限、异常处理；
- 制作原型优先的交互式 PRD（可点击原型与需求文本联动）；
- 评审前排查 PRD 的决策缺口与自相矛盾之处。

不适用：

- 技术架构、接口设计、数据库设计等实现层文档（PRD 只描述产品行为）；
- 独立的市场调研或竞品分析（应先完成调研，再进入需求撰写）；
- 只有视觉稿而没有任何需求说明的纯原型。

## 核心原则

1. PRD 回答"产品应该怎么做"，不回答"代码应该怎么写"。
2. 功能规格是文档主体，应占据最大篇幅。
3. 范围按"最小完整闭环"划定：用户能进来、能把事办完、出了问题能恢复。
4. 不编造数据。未知的指标、费率、限额、阈值标注 `【待定】`；按推测填写的内容标注 `【假设，待确认】`。
5. 同一角色、对象、状态、计算规则，全文只允许一个定义。
6. 用文字消除歧义，而不是用篇幅撑场面。

## 第一步：盘点输入

动笔前读完用户提供的全部材料，把信息分为四类：

| 类别 | 含义 | 处理方式 |
|---|---|---|
| 已确认事实 | 用户明确给出，或有具名来源支撑 | 可直接作为需求依据 |
| 产品判断 | 由上下文推导出的决策 | 影响范围或流程时写出推导理由 |
| 待确认假设 | 为推进文档而做的合理推测 | 标注 `【假设，待确认】` |
| 待办问题 | 缺失且会实质改变产品形态的信息 | 标注 `【待定】`，必要时提问 |

在内部先想清楚（不必单独成章）：主要使用者是谁、要达成什么结果；什么事件触发流程；什么状态证明事情办完；多角色场景下串联各方的业务对象是什么（订单、工单、申请……）；哪些操作涉及钱、权限、发布、删除、审批等不可逆后果。

## 第二步：提问策略（碎片输入补全）

总原则：用默认值推进，用提问兜底。

1. **先给方案，再问确认。** 不问"你想要什么"，而是给出"我打算这样处理：……，如不对请指出"。把开放式提问变成确认式提问，降低对方回答成本。
2. **只在答案会实质改变产品时才提问。** 值得提问的情形：涉及金钱、权限边界、合规要求、主流程走向、不可逆操作。字段默认值、文案细节这类问题自行假设并标注即可。
3. **一次性批量提问。** 把所有阻塞性问题集中列出（编号 + 默认处理方案），避免来回多轮。
4. **不阻塞产出。** 即使存在待办问题，也用标注好的假设把文档写完整——评审者需要看到成稿，而不是一堆问句。
5. **优先级缺失时按价值与风险预排**，无法确认的条目标注后请用户在评审时裁定。

## 第三步：选择文档模式

| 模式 | 载入参考 | 判断信号 |
|---|---|---|
| 常规文档 PRD | `references/prd-outline.md` | 默认模式。章节式文档，原型或示意图嵌在对应功能章节内 |
| 原型优先交互式 PRD | `references/interactive-mode.md` | 用户明确提出"交互式 PRD""原型优先""可点击原型与需求联动""左右分屏" |

- 只说"写个 PRD"时走常规模式；
- 常规模式也可内嵌演示，仅内嵌演示不构成原型优先；
- 仅当两种模式都讲得通、且选择会实质改变交付物时，才询问用户。

## 第四步：组织标准结构

完整 PRD 的标准章节如下。小迭代可合并精简，受监管或高风险流程应在此基础上扩充。

### 1. 背景与问题
说清"为什么做"：观察到的现象或证据 → 受影响的用户与场景 → 产品层面的应对决策 → 期望的可观察结果。禁止堆砌口号。

### 2. 目标
目标必须可验证。缺乏可靠数据时写定性结果（如"被驳回的提交可保留已填内容重新提交"），不编造量化指标；有基线数据时才写数字目标。

### 3. 范围
按最小完整闭环划分：

- **P0**：完成主流程与关键失败恢复所必需；
- **P1**：主流程跑通后显著降低使用成本或信任门槛；
- **明确排除**：容易被误认为包含、实则不做的内容（防止评审争议）。

不要惯性罗列登录、设置、消息通知、数据看板——只有参与主流程时才写入。

### 4. 用户故事
用"角色 + 场景 + 目的"描述需求来源，建议格式：

> 作为【角色】，在【场景/触发条件】下，我希望【动作】，以便【达成的结果】。

每个 P0 功能至少对应一条用户故事；故事与功能规格之间用编号互相引用，保证可追溯。

### 5. 功能规格（文档主体）
两种组织方式选一：

- **按模块分节**（模块 ≥3 时）：每个模块写清用途、触发条件、处理规则、结果与状态变化、字段、权限、异常；
- **需求条目表**（条目 ≤5 且行为扁平时）：编号、能力名称、用户与触发、产品行为、规则与状态。

任何重要功能都要写完整条行为链：**触发 → 处理规则（校验/计算/排序/依赖）→ 结果与可见反馈 → 状态变更**。因果逻辑用段落，可枚举内容（字段、状态、权限、计算规则）用表格。

### 6. 边界与异常
对每个重要动作逐一回答：校验失败怎么办？为空、被占用、冲突怎么办？超时与重试怎么办？用户中途取消怎么办？失败后能恢复到什么状态？涉及钱、权限、发布、删除、审批的操作还须定义：确认方式、防重复提交、成功凭证、撤销或补偿路径、通知对象。

### 7. 指标
仅在用户要求或领域确有需要时编写。写清：衡量什么事件、由谁触发、统计口径、期望方向。没有依据的目标值标注 `【待定】`，不要编造。

### 8. 排期
仅在用户要求时编写。给出里程碑与依赖关系即可；人力与工期没有可信依据时标注待定，不虚构数字。

### 共享规则
被多个模块引用的规则（权限矩阵、对象生命周期、计算与舍入、通知时机）集中到一处定义，功能章节按名称引用，不重复展开。

## 第五步：评审前自查清单

交付前逐项核对（该清单本身不进正文）：

| 检查项 | 通过标准 |
|---|---|
| 产品契约 | 主要用户、触发条件、核心任务、完成判定四者齐备 |
| 范围闭环 | 每个 P0 功能都服务于完成主流程或失败恢复；无投机性功能 |
| 行为链完整 | 重要功能均写清触发、处理、结果、状态变化 |
| 故事可追溯 | 每条 P0 用户故事有对应功能规格，反之亦然 |
| 口径一致 | 角色、对象名、字段、状态、权限、计算公式全文无矛盾 |
| 边界覆盖 | 校验、为空、冲突、失败、取消、重试等异常均有交代 |
| 重大操作安全 | 确认、防重、凭证、撤销/补偿、通知、升级路径按需定义 |
| 无虚构 | 未知数字与规则保持可见标注，未擅自补全 |
| 无越界 | 未出现框架、库表、接口等实现层决策 |
| 无注水 | 无空章节、无重复结论、无凑字数的套话 |

未通过的项先修订再交付。

## 写作纪律

- 写可观察的行为，不写"提升体验""优化流程"这类无法验证的表述；
- 术语采用业务方已有叫法，全文统一；
- 同一条规则只在一处定义，其他位置引用名称；
- 评审用问题集中放在"待办问题"一节，且只放实质影响决策的；
- 文档中不出现"自查清单"字样，不叙述写作过程。

## 输出格式约定

- 用户指定格式时从其指定；
- 未指定时：常规模式产出结构化 Markdown/文档，原型优先模式产出单个自包含 HTML 文件；
- 交付物必须是成稿，只交提纲视为未完成。
