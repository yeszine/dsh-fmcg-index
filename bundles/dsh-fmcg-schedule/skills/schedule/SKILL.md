# schedule：周期性自动化实施规范

把"每天早上给我一份销售简报""每周一检查一遍依赖更新"这类**周期性诉求**，转化为可长期稳定运行的自动化任务。本技能不绑定任何特定宿主，给出通用的设计方法与各平台的落地路径。

## 一、适用范围

### 什么时候用

- 用户明确表达了**重复节奏**：每天、每周、每工作日、每小时、每月 1 号等。
- 用户想管理已有的周期任务：查看、改时间、暂停、恢复、删除、立即跑一次。

### 什么时候不用

- 一次性工作："现在帮我分析一下""明天下午三点提醒我一次"——前者是普通任务，后者是一次性定时，都不属于周期自动化。
- 用户只说"持续跟踪一下"却给不出节奏——先与其确认频率，不要替他编造。
- 正在执行某次周期任务的运行过程中，不要再嵌套创建新的周期任务（容易造成任务无限繁殖）。

## 二、cron 表达式速查

主流调度器（crontab、GitHub Actions、多数 agent 宿主）使用**五段式 cron**：

```
┌──────── 分钟 (0–59)
│ ┌──────── 小时 (0–23)
│ │ ┌──────── 日 (1–31)
│ │ │ ┌──────── 月 (1–12)
│ │ │ │ ┌──────── 星期 (0–7，0 和 7 均为周日)
│ │ │ │ │
* * * * *
```

### 常用表达式

| 需求 | 表达式 | 说明 |
|---|---|---|
| 每天 08:30 | `30 8 * * *` | |
| 每工作日 09:00 | `0 9 * * 1-5` | 周一到周五 |
| 每周一 10:00 | `0 10 * * 1` | |
| 每月 1 号 07:00 | `0 7 1 * *` | |
| 每 2 小时 | `0 */2 * * *` | 整点触发 |
| 每 15 分钟 | `*/15 * * * *` | 注意最小粒度限制 |
| 每天 22:00 与 06:00 | `0 22,6 * * *` | 逗号枚举 |

### 语法要点

- `*` 任意值；`,` 枚举；`-` 区间；`/` 步进（`*/10` = 每 10 单位）。
- "日"和"星期"同时指定时，多数实现按**或**语义执行，容易踩坑——二选一，另一个写 `*`。
- 五段式无法表达的需求不要硬凑：秒级/亚分钟调度、"每月最后一个工作日"、"每隔 90 分钟跨天"等，要么改用更高频的触发 + 任务内自行判断是否本次该干活，要么明确告知用户能力边界并给出替代方案。

### 时区纪律

- 创建任务前确认**调度器按哪个时区解释表达式**：crontab 通常用系统时区，GitHub Actions **一律 UTC**，多数 agent 宿主允许指定用户本地时区。
- 与用户沟通时间时始终使用其本地时间（如"每天早上 8:30"），落地时再换算成目标调度器的时区，并显式说明换算结果。
- 夏令时地区注意：UTC 换算出的表达式在夏令时切换后会漂移一小时，能选本地时区就不要用 UTC 硬换算。

## 三、任务设计方法

### 3.1 明确产出物

每个任务必须先回答"每次运行产出什么、送到哪"：

- **产出物**：一份简报 / 一次检查结果 / 一份数据快照 / 一条告警。
- **去向**：写入哪个文件、发到哪个聊天/邮箱/频道、还是仅记录日志。
- **格式**：固定的产出结构（如"结论 → 数据表 → 异常清单"），保证多次运行的结果可对比。
- **空结果策略**：本次没有新数据/没有异常时，是照常产出"无变化"说明，还是静默跳过——必须预先定义，避免用户误以为任务没跑。

### 3.2 写一份自包含的执行指令

周期任务在无人值守的全新上下文中运行，指令必须能脱离当前对话独立成立：

- 用用户视角写清楚：做什么、数据源在哪、输出到哪、质量要求、失败时怎么办。
- 把"照上次那样""就用上面那个文件"这类指代全部替换为具体路径、具体字段、具体口径。
- **时间窗口用相对表达**：写"汇总前一个自然日的数据"，而不是把今天的日期冻结进指令——否则任务每天都查同一天。
- 指令里不寒暄、不写问候语，也不塞调度信息（cron、时区属于调度配置，不属于任务内容）。

### 3.3 幂等性

同一时间点重复执行不应产生叠加副作用：

- 产出文件用固定路径或按日期命名（`report-2026-10-26.md`），重跑覆盖同名文件，而不是追加第二份。
- 对外发通知前先检查"这一期是否已发过"，可用标记文件、记录表或产出物存在性来判断。
- 写数据库/表格时按键 upsert，避免重跑产生重复行。

### 3.4 失败通知

无人值守任务最怕"安静地死掉"：

- 定义失败时的通知通道（邮件、IM、日志文件末尾追加醒目标记），并区分**任务失败**（脚本报错、依赖不可用）与**业务为空**（没数据但运行正常）。
- 通知里带上可行动的恢复线索：失败原因、最后一次成功时间、重跑方式。
- 连续失败多次应暂停任务并升级提醒，而不是无限重试。

### 3.5 创建前的依赖核验

对任务指令里显式点名的依赖逐项确认可用，但**只验存在性，不真正执行工作负载**（不要为验证而先跑一遍报表）：

- 脚本/文件：路径可访问，命名与输出约定符合 README 或配置要求。
- 数据源与连接器：已连接、授权有效。
- 执行环境一致性：本机可见的文件，远程调度环境未必可见——以任务实际运行环境为准核验。
- 依赖不可用就明说阻塞点，不要创建一个注定失败的任务。

## 四、各宿主落地方式

### 4.1 Windows 任务计划程序（Task Scheduler）

适合本机脚本类任务（批处理、PowerShell、Python 数据整理）。

- 图形界面：`taskschd.msc` → 创建基本任务 → 触发器选"每天/每周"。
- 命令行（用 `schtasks`）：

```powershell
# 每个工作日 09:00 运行日结脚本
schtasks /create /tn "DailySalesReport" /tr "powershell -File D:\jobs\daily-report.ps1" /sc weekly /d MON,TUE,WED,THU,FRI /st 09:00

# 查看 / 立即运行 / 停用 / 删除
schtasks /query /tn "DailySalesReport" /v /fo list
schtasks /run   /tn "DailySalesReport"
schtasks /change /tn "DailySalesReport" /disable
schtasks /delete /tn "DailySalesReport"
```

- 注意：脚本内使用绝对路径；需要访问网络盘/特定用户资源时配置"以指定用户运行"并保存凭据；机器睡眠会导致错过执行，可在任务属性里勾选"唤醒计算机运行此任务"或"错过启动后尽快运行"。

### 4.2 Linux crontab

适合服务器上的脚本与数据任务。

```bash
crontab -e        # 编辑当前用户的定时任务
crontab -l        # 列出
```

```cron
# 每天 08:30 生成销售简报并追加日志
30 8 * * * /usr/bin/python3 /opt/jobs/daily_report.py >> /var/log/daily_report.log 2>&1

# 每小时检查一次接口可用性，失败时输出到告警文件
0 * * * * /opt/jobs/healthcheck.sh || echo "$(date) healthcheck FAILED" >> /var/log/alerts.log
```

- 要点：crontab 环境变量极少，脚本内显式 `source` 所需环境或使用绝对路径；`%` 在 cron 行里是特殊字符（需转义为 `\%`）；时区取系统时区，跨时区部署时先 `timedatectl` 确认。
- 错过执行：cron 不会补跑机器关机期间的任务，需要补跑语义时改用 `anacron` 或 systemd timer（`Persistent=true`）。

### 4.3 GitHub Actions schedule

适合与仓库绑定的任务：依赖巡检、定时构建、数据同步、自动提 PR。

```yaml
name: weekly-dep-check
on:
  schedule:
    - cron: '0 2 * * 1'   # 每周一 02:00 UTC（= 北京时间 10:00）
  workflow_dispatch:       # 保留手动触发入口，便于"立即跑一次"

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/check-deps.sh
      - name: 失败时开 Issue 通知
        if: failure()
        run: gh issue create --title "依赖巡检失败 $(date +%F)" --body "详见本次运行日志"
```

- 注意：**cron 按 UTC 解释**，与团队沟通时间时做好换算；仓库长期无活动时 GitHub 会自动停用 schedule，需要约定定期保活或接受该行为；`workflow_dispatch` 同时承担"立即运行"职责。

### 4.4 定时型 agent 宿主

部分 agent 运行环境内置周期任务能力（按时唤起一个带指令的会话）。在这类宿主上：

- 优先使用宿主原生的任务管理接口完成创建、列表、暂停、恢复、删除、立即触发，不要绕开它自建调度器。
- 按第 3.2 节把任务指令写成自包含提示词；时间窗口一律相对化。
- 修改已有任务前先读取其当前定义，只改用户要求变更的字段；复制任务 = 读取原任务定义后新建，不复制运行历史。
- 立即触发一次 ≠ 修改任务本身；用户只要"暂停一段时间"就绝不动任务内容。
- 操作结果不确定（超时、无明确返回）时，先查询任务真实状态再决定是否重试，避免重复创建。

## 五、上线前检查清单

1. 节奏能用五段 cron 精确表达吗？不能 → 已与用户确认替代方案。
2. 时区确认了吗？调度器时区与用户本地时间的换算写清楚了吗？
3. 每次运行的产出物、去向、空结果策略定义了吗？
4. 指令是否自包含（无对话指代、时间窗口相对化）？
5. 重跑幂等吗？会重复发通知/写重复数据吗？
6. 失败有通知通道吗？通知里有恢复线索吗？
7. 依赖在**执行环境**里核验过了吗？
